# BODA 開發前架構共識與 AI 協作手冊

## 0. 文件定位

這份文件是 BODA 在開始開發、修正或新增功能前，提供共同開發者、設計、QA 與 AI/LLM coding 使用的共同語言。它不只描述「現在有哪些功能」，也定義每次變更應如何拆解、落在哪一層、如何保留使用者體驗，以及完成後如何驗收。

核心原則：

1. 先定義使用者要完成的任務，再決定修改哪個模組。
2. 視覺版位、資料欄位、狀態保存與輸出格式分開管理。
3. 共用行為集中在 Core／Runtime；個別版位差異留在 Block／Schema／CSS。
4. iframe 子系統不直接共享 DOM，透過明確的 bridge message contract 交換資料。
5. 任何功能都必須同時說清楚：輸入、狀態、畫布、輸出、錯誤路徑與回復方式。

## 1. 開發前共識：先回答六個問題

每個需求開始前，先用以下六問建立共識：

| 問題 | 要產出的答案 |
|---|---|
| 使用者要完成什麼任務？ | 一句話任務定義與成功條件 |
| 會影響哪個工作區？ | 主工作台、工單生成器、匯入工單、曝光資源、吸底、維修 |
| 哪一份資料是 source of truth？ | schema、主頁 state、JBP state、Bottom ProjectFile 或工單欄位 |
| 是否跨 iframe／跨工具？ | message type、發送者、接收者、初始化與變更時機 |
| 使用者如何知道成功或失敗？ | UI feedback、狀態文字、錯誤訊息、可重試動作 |
| 如何驗收？ | 靜態、結構、視覺、實機與回歸案例 |

### 1.1 需求分層

- **P0 使用者任務**：使用者看到什麼、點什麼、完成什麼。
- **P1 互動規則**：拖拉、縮放、上下移、切換、反勾選、手動覆寫。
- **P2 資料規則**：欄位、ID、版位、座標、顏色、狀態與版本。
- **P3 技術實作**：Core、Block、Renderer、Parser、Bridge、Export。
- **P4 驗收與風險**：舊資料、不同 ID、重整、慢載入、無痕與瀏覽器差異。

不要從 P3 直接開始。先確認 P0～P2，再選擇實作位置。

## 2. BODA 分層架構

```text
使用者任務 / UI
        ↓
工作區入口（主頁、生成器、匯入、JBP、吸底、維修）
        ↓
應用狀態與資料轉換（state / parser / snapshot / export）
        ↓
Core 核心（schema renderer / image layout / shared rules）
        ↓
Blocks / Schema（版位結構、欄位、限制、視覺角色）
        ↓
資產與輸出（圖片、CSS、XLSX、JSON、PNG、ZIP）
```

### 2.1 各層責任

| 層 | 責任 | 不應負責 |
|---|---|---|
| UI／UX | 入口、操作、提示、狀態回饋 | 直接改另一個 iframe 的 DOM |
| 工作區 | 組合流程、持有該入口 state、呼叫 parser/export | 重複實作所有版位規則 |
| Core | schema 渲染、圖片限制、共用格式化與工具行為 | 寫死某一個活動版位的特殊座標 |
| Block／Schema | 版位欄位、圖層、限制、角色與 metadata | 跨工作區的同步流程 |
| Runtime／Bridge | iframe 初始化、狀態同步、快照與輸出協調 | 取代來源 state |
| Export／Parser | XLSX/JSON/PNG/ZIP 的輸入輸出 | 偷改使用者未要求的內容 |

## 3. 積木式架構

BODA 的版位不是一張不可拆的圖片，而是一組可以組合、替換、驗證與輸出的積木。

### 3.1 Block 的標準組成

```text
Block
├─ identity       唯一 ID、名稱、系列、版本
├─ layout         畫布尺寸、格位、座標、圖片範圍
├─ layers         bg、logo、商品、人物、文字、CTA 等圖層
├─ fields         可輸入文字與欄位上限
├─ rules          數量、排序、互斥、可否移除、可否縮放
├─ theme          背景、文字、促標、圓標、卡片、CTA 角色
├─ interactions   拖拉、滾輪、右鍵、編輯、刪除、上下移
├─ export         PNG、JSON、XLSX、ZIP 對應方式
└─ qa             參考圖、尺寸、視覺與回歸案例
```

### 3.2 Block 的開發契約

新增或修正版位至少要同步檢查：

- `blocks/{id}/block.json` 是否完整。
- `blocks/index.js` 是否註冊且 ID 不重複。
- 版位 HTML/CSS/config 是否能獨立載入。
- 生成器是否能選取、排序與輸出。
- 匯入工單是否能解析並還原圖片、文字、顏色與範圍。
- 維修是否能掃描、分類、預覽與下載。
- 舊 JSON／XLSX 是否仍可讀取。

### 3.3 積木組合原則

- 同一積木只描述自己的責任；跨積木行為由 Core 或工作區協調。
- 「圖片範圍」是可驗證的限制，不只是畫布上的輔助色塊。
- 「文字欄位」同時包含內容、上限、格式化與禁用語狀態。
- 「版位 ID」與「檔名」都可能變動，跨環境還原要有 manifest／mapping。
- 任何自動選擇都必須允許使用者手動反選與覆寫。

## 4. Core 核心

### 4.1 Core 的定位

Core 是所有工作區可共用的行為層。它應該穩定、可測試、與活動文案及單一版位座標解耦。

目前重要核心能力包含：

- schema 載入與 `BNCore.renderInstance` 渲染。
- 圖片比例、裁切、拖拉、縮放與範圍限制。
- 商品、人物、贈品、簽名檔的同區域空間計算。
- 文字 `$` 符號、千分位、禁用語與右鍵暫免格式化。
- 角色配色與深／亮背景下的可讀性規則。
- 狀態快照、版本相容與輸出前同步。

### 4.2 Core 修改判斷

若規則同時適用於兩個以上工作區，優先放 Core；若只適用於一個版位，留在 Block／CSS；若只影響資料交換，放在 Parser／Bridge；若只影響提示與排列，放在 UI。

### 4.3 Core 不變量

- 不破壞既有 `blockId`、欄位 key 與舊版 JSON 讀取。
- 不把 UI 顯示文字當作資料 key。
- 不用單一畫布的像素座標直接套到不同尺寸畫布。
- 不在截圖或下載流程偷偷改變使用者 state。
- 不讓一個 iframe 的初始 state 覆蓋另一個 iframe 的已編輯 state。

## 5. 工作區與使用者體驗

### 5.1 標準工作流

```text
選版位／等級
  ↓
排序、排數、選擇版配
  ↓
編輯文字、圖片、配色與規則
  ↓
明確載入到匯入工單
  ↓
在匯入畫布做工單層級修正
  ↓
同步吸底資料與結果
  ↓
預覽、驗證、下載 PNG／JSON／XLSX／ZIP
```

### 5.2 UX 原則

1. 使用者正在看的頁簽、捲動位置與選擇狀態不可因拖拉而跳走。
2. 自動連動可以提供預設，但不能鎖死使用者的反選與手動覆寫。
3. 任何長時間工作都要有進度、目前步驟與失敗後可重試方式。
4. 圖片編輯要有可見範圍、可拖拉、可縮放，且不可超出規則範圍。
5. 匯入後要能看見「吃到什麼資料」，不能只顯示抽象成功訊息。
6. 預設值、手動值、同步值要能區分，避免重整後覆蓋使用者結果。

### 5.3 UI 狀態模型

每個互動元件至少有：

- `idle`：尚未操作或待填。
- `loading`：讀取資產、解析工單或渲染中。
- `ready`：可以操作與輸出。
- `dirty`：有尚未輸出的使用者變更。
- `syncing`：跨 iframe／跨頁同步中。
- `success`：操作完成且可追蹤結果。
- `error`：失敗原因與可重試動作。

## 6. 人類與 AI/LLM 共讀的開發文件

AI coding 不應只收到「幫我改好」，而要收到可驗證的變更契約。

### 6.1 AI coding 任務格式

```text
需求名稱：
使用者目的：
影響工作區：
不變條件：
source of truth：
允許修改檔案：
禁止修改範圍：
輸入與輸出：
狀態／事件流程：
成功畫面：
錯誤與回復：
舊資料相容：
驗收案例：
```

### 6.2 給 AI 的執行順序

1. 先讀取相關 `AGENTS.md`、README、Core、Schema 與測試文件。
2. 先搜尋現有實作與事件名稱，不要直接新增平行邏輯。
3. 說明 source of truth 與會被影響的下游消費者。
4. 先做最小修改，再執行語法、結構與回歸檢查。
5. 若發現需求與現況衝突，列出衝突、採用的假設與風險。
6. 回報修改檔案、行為變化、驗收結果與尚未驗證的部分。

### 6.3 AI 不應做的事

- 未讀現有資料契約就重寫整個模組。
- 用預設值覆蓋已存在的使用者編輯。
- 把不同版位的 ID、檔名與座標視為永遠相同。
- 只驗證畫面，不驗證下載、重整、舊檔與跨環境還原。
- 為了讓測試通過而刪除錯誤提示或放寬真實限制。

## 7. 狀態、事件與跨工具同步

### 7.1 狀態擁有者

| 狀態 | 擁有者 | 其他工具取得方式 |
|---|---|---|
| 生成器版位選擇 | 主頁 generator state | 明確載入、快照、工單輸出 |
| 匯入工單畫布 | Import view state | XLSX／JSON／生成器版配 |
| JBP 版位編輯 | JBP state | postMessage、暫存 JSON、ZIP |
| 吸底編輯 | Bottom ProjectFile state | parent bridge、嵌入 JSON、工單內藏資料 |
| Block 定義 | block.json／registry | Core renderer、維修、輸出 |

### 7.2 Bridge 訊息規則

```text
READY              子工具準備完成
WORKORDER_FILE     傳送工單與可選的 bottomState
BOTTOM_STATE       傳送已編輯的吸底 ProjectFile
STATE              回報目前 state
STATE_APPLIED      回報 state 已套用
EXPORT_ALL         要求子工具輸出全部圖片／ZIP
EXPORT_RESULT      回報輸出成功或失敗
NO_WORKORDER       明確告知缺少工單來源
```

初始 state 與使用者變更必須區分。初始 state 只能作為備援；`changed: true` 才能成為雙向同步的最新編輯結果。

### 7.3 同步驗收

- 新工單／Demo 工單進來後，生成器吸底與獨立吸底都能取得資料。
- 在任一吸底入口編輯後，另一入口能同步且不循環覆蓋。
- 重整後不以預設 state 覆蓋最後一次使用者編輯。
- 換 ID、換 domain／port、無痕模式與清除網站資料後，舊格式仍可讀取。
- 下載全部時，主工單、吸底試算表、吸底圖片與 JSON 使用同一份最新 state。

## 8. 輸入、輸出與版本相容

### 8.1 輸入

- XLSX／XLSM 工單。
- 生成器目前選擇的版配。
- Demo 工單與同層圖片。
- JSON 暫存檔／專案檔。
- 本機 Logo、商品、人物、背景與 Icon。

### 8.2 輸出

- 畫布 PNG。
- 單獨或 ZIP 圖片。
- 生成器／匯入工單 XLSX。
- JSON／ProjectFile 暫存。
- 下載全部的主工單與吸底附加輸出。

### 8.3 相容策略

- 新格式增加欄位時，舊欄位仍可讀取。
- 新 ID 與舊 ID 不同時，使用 `layoutManifest`、ID map 或檔名 map 還原。
- `true`／`false` 勾選值要明確保存，不能以「欄位不存在」代替 false。
- 大型圖片 data URL 要在狀態與檔名索引中各自保留可追蹤映射。

## 9. QA 四層驗收

| 層級 | 檢查內容 |
|---|---|
| L0 靜態 | 語法、檔案路徑、registry、JSON schema、diff |
| L1 結構 | 欄位、ID、事件、state、manifest、輸出檔案 |
| L2 視覺 | 尺寸、位置、裁切、文字可讀性、範圍、重疊 |
| L3 實機 | HTTP server、瀏覽器、重整、慢載入、無痕、跨環境 |

### 9.1 每個功能至少要測

1. 首次使用與已有暫存兩種狀態。
2. 部分選取、全部選取、全部反選。
3. 圖片載入慢、圖片缺失、資料為空。
4. 立即下載、重整後下載、重新匯入後下載。
5. 手動覆寫後是否仍尊重覆寫結果。
6. 錯誤訊息是否指出原因與下一步。

## 10. 共同開發者交接格式

每次交接至少包含：

- 需求與使用者任務。
- 影響範圍與不影響範圍。
- 修改檔案與 source of truth。
- 資料格式／事件格式變化。
- UI／UX 行為變化。
- 已完成的驗收案例。
- 未完成、風險、假設與下一步。

## 11. 新功能範例：新增一個曝光版位

```text
1. 確認 PSD／參考圖、畫布尺寸、文字與圖片範圍
2. 建立 HTML／CSS／config.css
3. 建立 block.json 與 registry entry
4. 定義欄位、上限、顏色角色與互斥規則
5. 接上 JBP 預覽、Logo／商品／人物／背景訊息
6. 接上生成器選擇與匯入工單 parser
7. 接上維修掃描、分類與 QA 預覽
8. 驗證 PNG、JSON、XLSX、ZIP 與重整還原
9. 補上變更紀錄與交接說明
```

## 12. 交付判定

一項功能只有在以下條件都成立時才算完成：

- 使用者流程說得清楚。
- UI 狀態與錯誤路徑完整。
- 修改落在正確架構層。
- Core／Block／Parser／Bridge 的責任沒有混在一起。
- 新舊資料都能處理。
- 預覽、輸出、保存、重載與跨入口同步一致。
- 有可重現的驗收案例與交接紀錄。
