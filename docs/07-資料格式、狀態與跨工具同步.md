# 07｜資料格式、狀態與跨工具同步

文件狀態：現行程式字串、資料結構與主要流程已確認

盤點日期：2026-08-26

## 1. 資料流總覽

```text
XLSX / JSON / 圖片
       │
       ├─ 主 BOD parser ──> generator/import state ──> schema renderer ──> PNG/XLSX/JSON
       │
       ├─ bottom importer ──> bottom store ──> Konva ──> PNG/ZIP/project JSON
       │
       └─ JBP importer ──> shared editor state ──> layout iframes ──> PNG/ZIP/state JSON
```

三個子系統的資料模型不相同，只有在明確 bridge（按鈕、工單 parser、postMessage、共用 storage key）處才互通。

## 2. 主 BOD 工單與快照格式

### 2.1 生成器 state

主生成器的核心 state 以以下概念保存：

```text
GeneratorState {
  group,
  slots,
  msbn
}
```

其中 `slots` 表示版位選擇/順序與欄位資料，`msbn` 表示 MSBN 相關選擇與資料。實際 export 由 `buildWorkOrderGrid`、`exportWorkOrderJSON`、`exportWorkOrderXlsx` 等函式產生，欄位契約受 `wo-fields`、`wo-msbn-fields` 與 active block schema 共同約束。

### 2.2 匯入畫布 state

localStorage key：`wo_import_state_v1`

目前保存的概念格式：

```json
{
  "version": 2,
  "source": "…",
  "generatorSignature": "…",
  "columns": [
    {
      "blockId": "…",
      "data": {},
      "header": "…",
      "band": "…",
      "sourceKey": "…"
    }
  ]
}
```

`source` 用來辨識匯入來源，`generatorSignature` 用來辨識按鈕載入的生成器選擇；它們不應被當成使用者文字資料本身。

### 2.3 匯入快照

`buildImportSnapshot()` 產生：

```json
{
  "type": "wo_import_snapshot",
  "version": 2,
  "savedAt": "…",
  "source": "…",
  "generatorSignature": "…",
  "columns": [
    {
      "blockId": "…",
      "header": "…",
      "band": "…",
      "sourceKey": "…",
      "data": {}
    }
  ],
  "uploadedImages": [
    {"name": "…", "url": "…", "baseUrl": "…"}
  ],
  "theme": {},
  "imageZoomWeights": {},
  "imageOffsets": {}
}
```

快照會把可用的 blob URL 轉成 data URL，目的是讓下載或再次載入不依賴短命的 `blob:` URL。

大型快照（2026-11-06 補充）：

- 寫出：`compactImportSnapshotForStorage()` 把重複的大型 dataURL 收進 `_bodaAssetsV3` 素材表（`version` 變成 3，欄位裡改存 `__BODA_SNAPSHOT_ASSET_V3__:索引`），再由 `importSnapshotJsonBlob()` 分段寫成 Blob，不會產生一條巨型字串。
- 讀回：`.json` 超過 64 MB（`IMPORT_JSON_STREAM_THRESHOLD`）時，`handleImportFile()` 改用 `parseLargeJsonBlob()` 逐段解析位元組，每個字串值各自解碼，結果與 `JSON.parse` 相同。以前一律 `readAsText` + `JSON.parse`，超過瀏覽器單一字串上限（約 5 億字元）時會讀成空字串，出現「Unexpected end of JSON input」。
- 檔案真的被截斷時，錯誤訊息會寫明在幾 MB 處結束，提示改用完整原始檔。
- 快照會變大，多半是代言人或商品原圖解析度太高：例如 3000×6400 以上的 PNG，單張 dataURL 就有 75–137 MB，而且 `baseUrl`（編輯前的原圖）也會一起存。

## 3. 主 BOD localStorage keys

目前程式可見的主要 key：

| key | 用途 |
| --- | --- |

| `wo_family_names_v1` | family 名稱/顯示設定 |
| `wo_unlocked_v1` | 維護/鎖定狀態 |
| `wo_import_state_v1` | 匯入工單 state |

## 4. 主 BOD 的同步邊界

### 4.1 生成器 → 匯入工單

現在是「明確按鈕觸發」而不是即時同步：

```text
Generator state ──(按載入工單生成器版配)──> Import columns/state
```

這個 bridge 會更新匯入畫布的版位與資料，但匯入畫布接手後可以獨立修改。不要在 generator render、view switch 或 input listener 中偷偷呼叫相同載入函式。

### 4.2 匯入畫布 ↔ JBP

主頁使用 `wo_shared_canvas_bg_v1`、`wo_shared_exposure_text_v1` 等 key 搭配 `pushExposureOverviewText`、`syncImportedExposureOverviewText`、`pushImportBgToExposure`、`syncImportBgFromExposure` 做有限度同步。這不是完整雙向資料庫；應明確區分「共享摘要/背景」與「完整版位內容」。

代言人（2026-11-09 補充）：

- 讀取：`parseWorkbookOverviewEndorser()` 在「工單總覽」以標籤定位，「代言人照+簽名檔路徑(將取代2品)」右邊一格是兩張圖的檔名（逗號、＋號或換行分隔，`splitEndorserFileNames()`），「代言人小字」右邊一格是小字。只看緊鄰的一格，取第一組有填的值。
- 保存：`wo_shared_exposure_text_v1` 多了 `endorserFiles`（以換行分隔）與 `endorserNote`。
- 推送：`pushExposureOverviewAssets()` 的 `wo-workorder-overview-assets` 多了 `endorsers`（照欄位順序，用 `baseUrl`，不含商品影子）、`replaceEndorser`、`endorserNote`。
- 曝光資源端（shopee）：`bn-editor-plugin.js` 依檔名 → 圖片特徵 → 欄位順序分辨代言人照與簽名檔，存成 `_bnEndorserPhoto`／`_bnEndorserSign`／`_bnEndorserNote`。同一包重送時不覆蓋手動調整。畫布規則（只放在 ddcard、IG、HBN、LPBN、Coin、FB POST、SCBN、活動總覽、SBA、AMS；有代言人時商品只顯示 1 件；小字 24px@1200 寬、鎖定字級不提供滾輪縮放、自動黑白字）在 `layout-runtime.js`。

代言人跨版位連動（2026-11-09 改版）：

- 指標版位：HBN 是主要指標、LPBN 是第二指標。改 HBN → 所有鎖定版位跟著；改 LPBN → 「LPBN 那組」跟著，並記下 `_bnEndorserNote.lpbnOwnPhotoId`，之後再改 HBN 不會蓋掉 LPBN 那組（換一張代言人照才重新全部跟 HBN）。改其他版位只動自己和同名的方／橫版（`getPairedLayoutIds`）。分組：寬高比 < 3.2（比 HBN 方，FB_POST、ddcard、IG、Coin、SBA_APP）屬 LPBN 組，其餘屬 HBN 組（`endorserGroupOf`）。
- 位置格式：代言人照存 `efr`（同時記「畫面高度」與「商品區高度」兩種單位的大小、頭頂位置、靠邊距離）；橫式版位用畫面高度換算、直式（ddcard、IG）用商品區高度，照片框永遠是圖片比例。簽名檔存 `textRel`（靠照片哪側、離照片邊幾個字級 em、垂直中心在照片高度的比例、寬度幾個 em）；小字存 `noteRel`（相對簽名檔左上角的 em 位移，沒有簽名檔才相對照片）。em＝該版位小字字級，所以簽名＋小字是一組固定大小的文字塊。每筆都帶 `src`（在哪個版位調的）。
- 自動配合：`src` 不是自己的版位時，`fitEndorser()` 保證人像左右與上方不出框（下方可出血）、簽名＋小字整塊不出框，並避開文字區（主標、副標、日期、品牌名、LOGO）；壓到時依序試「往人像那側移 → 往下移 → 整組等比縮小」。CTA 是軟限制：簽名／小字被蓋住超過 12% 才挪文字塊，不縮人像。在該版位手動拖曳後（`src`＝自己）就不再自動調整。
- 舊暫存轉換：iframe 就緒時若指標版位存的代言人照沒有 `efr`，`requestEndorserMigrationIfNeeded()` 只請一個指標版位（有載入的 HBN 優先，沒有才用 LPBN）以新規則重報一次（`bn-endorser-repost`，訊息帶 `migrate`，不算 LPBN 自己調過）。已是連動來的位置不會被晚到的快照倒回。

### 4.3 主頁 ↔ iframe

iframe bridge 應遵守：

- parent 等 child ready 後再送需初始化的資料，或允許 child 重播 ready 後補送。
- payload 需要版本或 type，避免把一般 window message 誤判為工具事件。
- child 的完整內部 state 不應被 parent 直接改寫。
- download/snapshot 應由實際擁有 DOM/canvas 的子系統完成。

## 5. 吸底圖 project JSON

格式定義：[`bottom/src/state/projectFile.js`](../bottom/src/state/projectFile.js)

| 欄位 | 說明 |
| --- | --- |
| `format` | `sticky-banner-project` |
| `version` | 目前為 2 |
| `savedAt` | 存檔時間 |
| `activeBannerIndex` | 目前 banner |
| `sharpen` | 匯出銳化設定 |
| `banners` | banner/slot/顏色/圖示/文字資料 |
| `customIcons` | data URI 圖示 |

v1 的單 slot 格式會被包裝成 v2，這是現行相容策略。任何 schema 變更都要加入 migration 與壞檔錯誤訊息。

## 6. JBP persistence

JBP 使用雙層保存：

- IndexedDB：`bn_editor_state_db` / `states` / `current`，保存完整 state 與大型圖片。
- localStorage：`bn_editor_state_v1` 與 full/light fallback，保存可快速啟動或無 IndexedDB 時的退路。

除錯順序建議：先記錄資料來源與 version，再分別檢查 IndexedDB、localStorage、iframe 的 runtime state；不要在未備份的情況下直接清除全部。

## 7. XLSX 邊界

目前至少有三種 XLSX 消費者：

| 消費者 | 解析器 | 目的 |
| --- | --- | --- |
| 主 BOD | ExcelJS 4.4.0 | 生成/匯出工單、解析自有工單 |
| bottom | SheetJS 動態 CDN | 吸底圖工單匯入 |
| JBP | SheetJS 動態 CDN | 工單、版位詳情表、banwords |

同一個 `.xlsx` 不代表三個 parser 的欄位語意相同；修改工單欄位時要分別跑三個入口的解析測試。
